## Accessibility context and geometry

The helper imports macOS Accessibility APIs including `_AXUIElementCopyAttributeNames`, `_AXUIElementCopyAttributeValue`, `_AXUIElementCopyMultipleAttributeValues`, `_AXUIElementCopyParameterizedAttributeValue`, `_AXUIElementCopyElementAtPosition`, `_AXObserverCreate`, `_AXObserverAddNotification`, `_AXObserverGetRunLoopSource`, `_AXObserverRemoveNotification`, and `_AXUIElementSetMessagingTimeout` (native symbol-table extraction, lines 1011–1030). The binary therefore has both AX tree-reading and notification machinery; the symbol table alone does not prove which requests use each API.

Native IPC strings include `AppContextUpdate`, `AppContextHTML`, `AccessibilityTreeHTML`, and `SetAccessibilityTreeCapture` (native string extraction, lines 11886–11889). The embedded payload field names include `nearestTexts`, `elementDescription`, `focusedElement`, `htmlContents`, `windowTitle`, `markerRangeNSRange`, and `markerRangeStringValue` (lines 12212–12222). The AX collection path has log anchors `Beginning AX context collection`, `Sending AppContextUpdate request with nearestTexts length`, and `Sending AppContextHTML request with htmlContents with length` (lines 14445–14455). This supports separate text/description and HTML context payload paths.

The helper also contains selected-text and caret-related anchors: `AXSelectedTextRange`, `AXSelectedTextRanges`, `AXSharedCharacterRange`, `AXIndexForTextMarker`, `AXStartTextMarker`, `AXSelectedTextMarkerRange`, `AXStringForRange`, `AXNumberOfCharacters`, and `AXVisibleChildren`. Its strings describe returning selected-text information from parent, text-area, static-text, or text-field nodes, and a fallback `Getting selected text via copy`. The HTML template contains `<mark class="insertion-point">&lt;USER INSERTING TEXT HERE&gt;</mark>` and `data-selected="true"` (lines 15168–15197, 15419–15435). Together these are good evidence that selection and insertion-point position are represented, though they do not reveal which representation is sent for every target app.

The embedded "Accessibility Tree" HTML/CSS uses `.ax-element { position: fixed; ... }`, hides empty elements with `.ax-element:empty { display: none; }`, clips `[data-role="AXScrollArea"]`, and assigns z-index by element nesting depth and text presence (lines 15346–15410). `AXPosition` and `AXSize` also occur as native strings (line 20945–20946), and `_AXUIElementCopyElementAtPosition` is imported. This suggests a layout-aware accessibility-tree renderer. The extracted template does not expose a `left`/`top` interpolation, and the string table does not prove that position/size values are populated or that this HTML is the exact `AppContextHTML` payload. The empty-node CSS hides elements in the HTML rendering; it does not establish that the AX traversal prunes those elements. The native payload has `includeOffscreen` and `isVisible` field names (lines 12475–12476). Caller-side cross-check: `main.pretty.js` in the extracted ASAR passes `includeOffscreen = isInstructMode` and `captureMarkerContext = internal.shouldSaveAxText` in `DictationStart` (around line 235391); the marker-text capture preference defaults to false. Thus off-screen inclusion is caller-controlled and tied to instruct mode, while the meaning of `isVisible` and the precise geometry encoding remain unclear from native strings.

The helper logs `Setting 'AXManualAccessibility' succeeded` and the corresponding failure (lines 15439–15442), and imports `_AXUIElementSetAttributeValue`. This supports an attempt to set that AX attribute during setup, potentially to improve access to Chromium-backed AX trees. The exact target and call conditions are not recoverable from strings; this is not evidence that every Electron app needs the setting. A separate native payload field is named `screenReaderMode` (line 12230); other strings say `Screen Reader Optimized` and `Found Screen Reader Optimized mode is on` (lines 15459–15461). Those strings support detecting an app-level mode that is already on. They do not show that Flow enables macOS VoiceOver or turns on the detected mode.

## Isolation and responsiveness

This is a separate signed helper app bundle, and native strings say `Launching swift helper app`. Its IPC implementation has stdin-reader and message-queue strings, a `defaultRequestTimeout` field, `Request timed out, clearing pending response`, `Received consecutive timeouts, terminating helper process`, and `IPC request processing exceeded time threshold` with `processingTimeMs` (lines 14493–14512). This is evidence of a separate process and a repeated-IPC-timeout termination path. The containing Electron app also has a watchdog/close-and-relaunch path (`main.pretty.js` around lines 240727 and 241400), so recovery is supervised by the parent process rather than established as a helper self-restart.

`_AXUIElementSetMessagingTimeout` is an imported ApplicationServices symbol, with `setMessagingTimeout` also present as a selector/string. This supports a configurable AX messaging-timeout mechanism, but the binary strings do not reveal its configured value or prove that every AX call is covered. The HTML walker has explicit budget-failure anchors: `Ran out of time while converting AX to HTML, returning empty string. Time elapsed: ...`, `Could not process element hierarchy fast enough. Time elapsed: ...`, and `Could not collect text fast enough. Time elapsed: ...`; Cursor collection also logs a maximum element limit. The numeric limits are not recoverable from these strings. The `Stopping edited text listener due to 60-second timeout.` message belongs to post-paste edit observation, not the AX tree walk, and should not be used as an AX timeout value.

## App-specific context and edit observation

`CursorContextUpdate` has payload fields `fileNames`, `screenReaderMode`, `textAreaContents`, and `focusedElementContents` (native string extraction, lines 12229–12232). Native anchors identify Cursor-like bundle IDs for the Cursor-designated app, Windsurf, and VS Code, log `Beginning Cursor-specific context collection`, and report reading `textArea/textField` content (lines 15446–15466). No LSP, language-server, or `textDocument` protocol strings were found; the static evidence supports accessibility-tree extraction, not LSP access.

The helper includes `quillDeltaToHTML` and Slack Texty/formatted-text extraction strings, including `Failed to extract Slack formatted text from clipboard, falling back to plain text` (native string extraction, lines 15198 and 15223–15228). It also names Safari and Chrome, and has `AXWebArea URL search found the web area`, `webArea URL scheme is not http or https`, and a `skip-url-search` feature flag (lines 15212, 15761–15766). These show targeted normalization and browser identification/URL lookup, but do not establish a universal browser DOM feed.

There is a post-paste edit-observation path: strings include `pasteId`, `pastedText`, `beforeTextBoxContents`, `afterTextBoxContents`, `UpdateEditedText`, and `Found dictated text in contents, doing edit analysis`. The listener observes `AXSelectedTextChanged` and `AXFocusedUIElementChanged`, requires an anchored dictated-text match, and stops after 60 seconds. This indicates capture of a bounded correction event; it does not show that corrections are retained as reusable vocabulary or model-learning data.

## Practical lessons and limits

The strongest design lesson for Kol is to make a context walk produce structured, inspectable AX output that preserves selected range/caret position and can optionally carry element geometry. The Flow bundle suggests an HTML tree representation, but its strings do not settle off-screen filtering or coordinate encoding. A second lesson is the boundary: isolate potentially blocking AX work and pair any IPC timeout with a supervisor that can terminate and relaunch the helper. Flow's binary proves process separation, AX messaging-timeout support, and termination after repeated IPC timeouts; its Electron supervisor supplies the close/relaunch path. No numeric per-call AX timeout is recoverable from the static evidence.

No OCR/Vision framework or OCR request symbols were found in the helper's linked frameworks or symbol/string searches. This is only a statement about this native helper binary; OCR could exist in Electron or another packaged component.
